# 金融工程手搓系列 — 写作框架与约定

> 本文档是系列写作的可复用基准。写任意一章前参考此文档。

---

## 一、系列设定

### 人物

- **YaHan**：第一人称叙述者。既是故事中的"我"，也是讲解者。角色固定，贯穿全系列。
- **你（读者）**：第二人称。作为对话方出现在故事中——借钱的、做生意的、签合约的、提问题的。读者被拉进场景里，不是旁观者。

### 世界观

- 从零构建。不使用任何金融库（numpy、scipy、math.exp 等均禁止）。
- 所有数学工具手搓（随机数、$e^x$、后续的正态分布等）。
- 定律：**代码即定义，输出即论证**。正文中的运行结果只能来自实际运行的 .py 文件。

### 层级类比

类比计算机体系结构（NAND to Tetris）：

| 计算机层 | 金融工程层 | 状态 |
|---|---|---|
| 逻辑门层 | 原语层（Ch1）| 写作中 |
| 运算电路层 | 组合层（Ch2）| 已完成 |
| 时序逻辑层 | 状态层（Ch3）| 规划中 |
| CPU 层 | 定价/对冲层（Ch4）| 规划中 |
| 应用层 | 结构化层（Ch5+）| 待定 |

## 二、十二步教学引擎（每章复用）

| # | 步骤 | 动作 | 检查项 |
|---|---|---|---|
| ① | **朴素入口** | 从一个零专业知识的场景切入，问一个简单到"不像金融问题"的问题 | 读者不需要任何前置知识就能理解这个问题 |
| ② | **埋下伏笔** | 列出场景里隐藏的全部概念，但不展开 | 用列表而非段落 |
| ③ | **角色锚定** | 用 YaHan + "你" 把场景具象化 | 每节至少出现一次角色 |
| ④ | **一次一个** | 每节只引入一个新概念 | 节标题只能包含一个新名词 |
| ⑤ | **先具体后抽象** | 具体数字推导 → 公式 | 数字必须在公式前 |
| ⑥ | **代码即定义** | Python 函数是概念的精确表述 | 函数名暗示概念（如 `interest_amount`） |
| ⑦ | **输出即论证** | 代码运行结果是正文的有机部分 | 输出必须来自实际 .py 文件运行 |
| ⑧ | **设问推进** | 每节结尾埋问题，下一节开头回答 | 问题以 `>` 引用格式出现 |
| ⑨ | **直觉先行** | 给公式前先给"它到底在说什么" | 至少一句话解释直觉 |
| ⑩ | **陷阱警告** | 明确标出容易想错的地方 | 至少每 3 节有一个陷阱提示 |
| ⑪ | **阶段盘点** | 每 3-4 节做一次"到这里我们多了什么" | 用表格而非段落 |
| ⑫ | **综合挑战** | 用一道题串起全章概念 | 题面简洁，求解步骤用到 ≥3 个本章概念 |

## 三、写作五准则

### 准则 1：变量首次出现带英文全称

格式：`面值 (Face Value, FV)`

- 中文术语在前，英文全称 + 缩写在后，用括号包裹
- 同一变量在同一章内首次出现时标注，后续直接用缩写
- 如果公式需要下标（如 $S_T$、$r_{\text{annual}}$），下标也附带解释

```markdown
✅ 面值 (Face Value, FV)：到期归还的本金。
✅ 交割价 (Delivery Price, K)：远期合约约定的交易价格。
❌ 面值就是到期归还的本金。
```

### 准则 2：代码输出全英文，且来自实际运行

- 所有 `print()` 语句输出英文
- 正文中 ` ```text ` 代码块的输出，必须来自对应 `fe_chapterN.py` 的实际运行结果
- 禁止手写或猜测输出
- 运行代码后再写正文：先跑 `fe_chapterN.py` → 复制输出 → 再写 markdown

```markdown
✅
```python
print("Principal:", P)
```
```text
Principal: 1000
```

❌
```python
print("本金:", P)
```
```text
本金: 1000
```
```

### 准则 3：降 AI 味，去"草稿"痕

**禁止项**：
- "不是 A，而是 B" 句式（过于规整、总结感强）
- "换言之""换句话说""也就是说" 的连续使用
- 以排比句收尾的总结段（"这就是 X，也是 Y，更是 Z"）
- 空泛的过渡句（"接下来让我们深入探讨……"）
- 草稿标记：`【补充】`、`TODO`、`草稿`、空括号 `【】`

**允许并鼓励**：
- 口语化转折："但有个问题""好，现在假设"
- 不完整的句子（在解释公式时）
- 直接的否定："不对。"
- 以代码块或表格替代总结段

### 准则 4：每章至少一个真实案例

- 案例可以是历史事件、公司故事、个人轶事
- 案例不一定要"完美对应"理论——有偏差的地方正好指出
- 案例节标题用 `举例：` 前缀
- 案例放在概念讲解完之后，综合挑战之前
- 参考第二章 §2.7 堂岛米会所的处理方式

案例来源参考：
- 历史：美索不达米亚利息法（公元前 2400）、斐波那契《计算之书》（1202）、美第奇银行（15 世纪）、荷兰郁金香（1637）、堂岛米会所（1730）
- 现代：1987 黑色星期一、1995 巴林银行、1998 LTCM、2008 次贷危机、2022 美债暴跌

### 准则 5：节标题标注类型

每节标题使用以下前缀：

| 前缀 | 含义 | 何时使用 |
|---|---|---|
| `构建：` | 引入新概念、新代码、新公式 | 本章的核心教学内容 |
| `检验：` | 用代码验证、测试理解、展示数值关系 | 让读者看到"它确实是这样" |
| `举例：` | 真实世界的故事或案例 | 每章至少一次 |
| `挑战：` | 综合练习题 | 章末使用 |

## 四、代码组织

### 文件命名

```
workbench/
  fe_chapter1.py       # 第 1 章全部函数 + 验证代码
  fe_chapter1_output.txt  # 运行输出存档
  fe_chapter2.py
  fe_chapter2_output.txt
  ...

docs/ 或根目录/
  FE_chapter1.md       # 第 1 章正文
  FE_chapter2.md
  ...
```

### Python 文件结构

```python
"""
Chapter N: [章节英文标题]
[一句话说明本章在做什么]
"""

# 从前面章节导入
from fe_chapter1 import present_value, CashFlow  # etc.

# ═══ §N.1 节标题 ═══════════════════════════════════════════

def function_name(param1, param2):
    """Docstring: 中文 + 英文术语."""
    ...

# ═══ Demo / verification ════════════════════════════════════

if __name__ == "__main__":
    print("=" * 60)
    print(f"Chapter {N} - [Layer Name] Verification")
    print("=" * 60)

    # --- §N.1 Section name ---
    ...
```

- 用 `├──` 或 `═══` 分隔节
- 验证代码放在 `if __name__ == "__main__":` 下
- 每节验证块用 `--- §N.x ---` 标识
- 输出中包含变量全称（如 `Face value (Face Value, FV): $1000`）
