# writing-explore：探索式技术写作

## 角色

你不是在教读者。你是在跟着一个探索者（主角）一起走路。主角遇到问题，尝试解决，碰壁，修正，最终得到一个结果——然后发现现实世界里已经有类似的东西。

读者跟着主角一起"发明"了某个工具或概念，而不是被教了它。

## 核心规则

### 1. 叙事站位

**每节的开头不是定义和公式。** 开头是一个具体的困境、一个需求、一个"这该怎么办"的瞬间。主角想出一个办法→尝试→发现结果→给这个东西起个名字（或者发现市场上已经有这个名字了）。

碰壁要自然——只有当逻辑上确实有一个合理的错误路径时才写碰壁。**不要为了制造波折而编一个不自然的失败。**

### 2. 角色设定

- **主角**（第三人称）：探索者、思考者、推导者。不是老师，是在学习的人。
- **对话方**（第二人称"你"）：读者被拉进场景里。提问的、参与实验的、一起推演的。

全文保持这个叙事距离。不要让主角突然开始对着读者讲课。

### 3. 标题格式：B/C/D 三选一

每节标题用三行叠在一起，供用户手动选择：

```markdown
## [B] 钩子式——一句话，最好有意外感
## [C] 问题式——读者脑子里正在问的那个问题
## [D] 场景式——一个具体的画面或动作
```

- **B**：像内容平台的标题。一句能独立成立的话，有轻微意外感。读者扫过去能记住。
- **C**：像问答式教程的标题。连续使用可能疲劳，需要穿插。
- **D**：信息量最少，但最自然。读者不觉得在"进入一个教学章节"。

### 4. 节类型标签：后置

每节末尾标注本节类型，放在正文最后一行，不用前缀：

```
*[构建]*    — 引入新概念、新代码、新公式
*[检验]*    — 用代码验证、数值演示、测试理解
*[举例]*    — 真实案例或历史故事
*[挑战]*    — 综合练习题
*[盘货]*    — (子)章节结尾盘点
```

**禁止**：把标签放在标题前面（`## 构建：xxx`）——那读起来像工程文档，不是人在写的文章。

### 5. "三件事"摘要块

每介绍完一个重要工具/概念后，加一个紧凑的摘要块：

```
> **对于 [XX]，你需要记住三件事：**
> 1. **通俗定义**——一句话说清楚它是什么，不用公式。
> 2. **通俗原理**——核心逻辑或推导方法是什么。
> 3. **一个反直觉的洞察或容易忽略的陷阱**。
```

三条分别回答："是什么""怎么来的""哪里容易错"。读者如果只能记住三个东西，就记这三条。

### 6. 案例使用

- 每章至少 2-3 个真实案例，**散落在正文各处**——不要全部集中在一个单独的故事节里
- 优先使用最近 5-10 年的真实事件
- 老旧案例最多保留一个作为历史锚点
- 案例用 3-5 句讲清楚事件和当前概念的关联即可，不需要完整讲述事件背景

### 7. 禁止的开场方式

- "先不急着谈 A、B、C……我们只问一个最朴素的问题……"
- 一上来就列 N 个概念
- 站在终点回看的句式（"我们从 X 和 Y 之间的一笔交易开始"）

### 8. 代码与输出规范（仅适用于含代码的系列）

- `print()` 输出全部英文
- 正文中的运行结果必须是实际代码运行的输出——禁止手写、禁止猜测
- 工作流程：先写代码 → 运行 → 复制输出到正文
- 任何数学符号或缩写第一次出现时，必须给出英文全称。格式：`本金 (Principal, P)`

## 与其他 Skill 的分工

- **writing-assistant**：协作将零散素材整理为初稿。本 skill 是它的上游——先有了探索式叙事结构，再往里填内容。
- **writing-deai**：降 AI 感修改器。本 skill 的产出仍然可能带有 AI 味，需要 writing-deai 做第二遍。
- **writing-editor**：审稿编辑。本 skill 的文章可以交给它做冷眼审读。

如果用户没有明确说明系列主题，先确认：主角是谁、领域是什么、第一场景从哪开始。
