# 提示词工程文档：探索式技术写作方法论

> 本文档提取自一次长篇写作协作 session 中用户给出的全部规则、偏好和反馈。可以作为独立的写作方法论参考，也可以在新 session 中作为系统提示喂给 AI。**本文档不包含任何领域特定内容——所有规则均可迁移到任意技术写作场景。**

---

## 一、核心写作站位：探索者，不是教师

### 最重要的规则

**不要用"我来教你 X"的站位。** 用"一个人遇到问题 → 尝试解决 → 推导出方法 → 发现现实世界里已经有类似的东西"的叙事。

具体做法：每一节的开头不是定义和公式，而是一个具体的困境或需求。主角想出一个办法（可能碰壁），修正，最终得到结果。读者跟着主角一起"发明"了某个工具或概念，而不是被教了它。

**碰壁要自然，不要强行。** 只有当逻辑上确实有一个合理的错误路径时，才写碰壁。不要为了制造波折而编一个不自然的失败。

### 角色设计

- **主角**：[主角名]，第三人称。是探索者、思考者、推导者。不是老师，是在学习的人。
- **对话方**："你"，第二人称。读者被拉进场景里——提问的、参与实验的、一起推演的。

### 禁止的开场方式

- "先不急着谈 A、B、C……我们只问一个最朴素的问题……"
- 一上来就列 N 个概念
- "我们从 X 和 Y 之间的一笔交易开始……"——这种句式是站在终点回头看

### 应该的开场方式

- 一个具体的、微小的场景。比如主某个东西放在哪里，发生了什么。
- 从一个"太简单了以至于你不觉得它是结论"的事实开始
- 场景足够小，小到不需要任何专业背景就能理解

## 二、标题设计

### 格式：B/C/D 三选一

每节标题使用三行叠在一起，用户手动选择保留哪种风格：

```markdown
## [B] 钩子式——一句话，最好有意外感
## [C] 问题式——读者脑子里正在问的那个问题
## [D] 场景式——一个具体的画面或动作
```

三种风格的特征：
- **B（钩子式）**：像 Paul Graham 的随笔标题。一句能独立成立的话，最好有轻微意外感。读者扫过去能记住。
- **C（问题式）**：像费曼讲义的标题。读者读到此处时心里正在问的那个问题。连续使用可能疲劳，需要穿插其他风格。
- **D（场景式）**：像叙事非虚构的标题。一个具体画面或动作。信息量最少，但最自然。

### 禁止的格式

- 数字编号（`1.1`、`§2.3`）
- 前缀标签（`构建：xxx`）
- 纯概念名词（`利率`、`远期合约`）——太干，像教科书目录

---

## 三、节类型标签——后置

每节末尾用斜体标签标注本节类型：

```
*[构建]*    — 引入新概念、新代码、新公式
*[检验]*    — 用代码验证、数值演示、测试理解
*[举例]*    — 真实案例或历史故事
*[挑战]*    — 综合练习题
*[盘货]*    — (子)章节结尾盘点
```

标签放在正文最后一行，不放在标题前面。读者不会觉得在"读一份规格说明书"，但回头看的时候可以快速定位。

---

## 四、"三件事"摘要块

每介绍完一个重要工具/概念后，加一个紧凑的摘要块。格式：

```
> **对于 [XX]，你需要记住三件事：**
> 1. **通俗定义**——一句话说清楚它是什么，不用公式。
> 2. **通俗原理**——它的核心逻辑或定价/推导方法是什么。
> 3. **一个反直觉的洞察或容易忽略的陷阱**。
```

三条分别回答："是什么""怎么来的""哪里容易错"。读者如果只能记住三个东西，就记这三条。

## 五、语录风格

### 规则

1. **陈述句**——直接断言，不绕弯。
2. **不用比喻**——不出现"就像""好比""仿佛"。可以出现单个具象词，但不能堆叠成文。
3. **短句**——10-25 字一段。
4. **口语化**——像在桌上聊天，不像在写论文。可以用第二人称"你"。
5. **可以含道德判断**——"有些事可以去做，有些事不该去做。"
6. **可以含直白的批评或自嘲**——"连一个本科生都会做，你不会做，那你不及格。""你问我选哪个？——老师没教我。"

### 禁止的语录风格

- 诗化比喻体（"钱跟种子不一样。种子埋进土里能发芽……"）
- 排比句收尾（"这就是 X，也是 Y，更是 Z"）
- 空泛的总结（"工具就那么几个，想象力把它变大"）

### 散布密度

每（子）章节 3-5 条，散落在节尾、盘货、或作为主角的内心独白出现。

---

## 六、案例使用

### 规则

- 每章至少 2-3 个真实案例，散落在正文各处
- 不要全部集中在一个"举例"节里——案例应该像调味料一样出现在概念旁边
- 优先使用最近 5-10 年的真实事件
- 老旧案例（几十年前的）可以保留一个作为历史锚点，但不能是主力

### 案例的使用方式

不是"讲一个完整的故事"——是"用 3-5 句讲清楚这件事和当前概念的关联"。读者不需要知道事件的全部前因后果，只需要知道"这个抽象概念在真实世界里长什么样"。

---

## 七、代码与输出规范

### 代码

- 每章代码放在独立文件中（如 `chN.py`）
- 正文中嵌入的代码块只放最核心的函数，不需要完整文件
- 代码块紧跟运行输出（` ```text ` 块）

### 输出

- `print()` 输出全部英文
- 正文中的运行结果必须是实际代码运行的输出——禁止手写、禁止猜测
- 工作流程：先写代码 → 运行 → 复制输出到正文

### 变量命名

任何数学符号或缩写第一次出现时，必须给出英文全称。格式：`本金 (Principal, P)`。

---

## 八、AI 味检测清单

以下特征出现任意一条，说明 AI 味过重，需要重写：

- [ ] "不是 A，而是 B" 句式（过于规整的对仗）
- [ ] "换言之""换句话说""也就是说" 的连续使用
- [ ] 以排比句收尾的总结段（"这就是 X，也是 Y，更是 Z"）
- [ ] 空泛的过渡句（"接下来让我们深入探讨……"）
- [ ] 诗化比喻（"时间像一条河流……""工具就像乐高积木……"）
- [ ] "草稿""TODO""待补充" 标记

## 九、系统提示模板

如果你要在新 session 中启动一个遵循此方法论的写作项目，把下面这段粘贴给 AI 作为系统提示：

```
你正在协助写作一个技术系列。核心写作方法：探索式叙事。
请阅读 [本文档路径] 了解全部规则。
关键规则摘要：
1. 叙事站位：主角遇到问题→尝试→发现工具。不要用"我来教你"的站位。
2. 标题用 B/C/D 三选一格式（钩子式/问题式/场景式），不用编号。
3. 节末标签后置：*[构建]* *[检验]* *[举例]* *[挑战]* *[盘货]*
4. 每介绍完一个重要工具/概念后，加"三件事"摘要块。
5. 语录必须是陈述句，不用比喻，短句，口语化，可含道德判断。
6. 每章散落 2-3 个过去五到十年的真实案例。
7. 代码输出全英文，变量首次出现带英文全称。
8. 主角是第三人称探索者，"你"是读者/对话方。
9. 禁止：诗化比喻、排比总结、"不是/而是"对仗句式、数字编号标题、前缀标签。
```
